# Mixio maintainer

Version: `2026-09-12.1`. This is a contributor operating skill, maintained in the configured shared tracking checkout and distributed as a versioned repository asset. The Skills CLI internal marker keeps it out of normal customer discovery; repository agents reach it through their instructions. It is not an access-control boundary.

Read this repository's [context guide](../../../docs/repository-context.md) for ownership and source entry points. Use the [tracking protocol](../../../docs/tracking-protocol.md) for root resolution, live ticket identity, service failures, and publication. Existing user authorization governs the work; this skill adds no permission to merge, deploy, accept memory, spend beyond the task, or contact others.

## Orient with focused context

Resolve the repository, branch/worktree, task, and your role. For implementation, read the live Plane acceptance criteria and dependencies before allocating work. For advice or a small lookup, retrieve only context that can change the answer; avoid inventing an execution project for a question.

Resolve the shared Link **data root** explicitly using the tracking protocol. Finding the `lnk` executable does not select its target. Pass the validated root to every workspace command, including retrieval and capture. A product checkout or temporary worktree is not an implicit replacement for company memory. Keep actual paths in user-local configuration; missing configuration follows the protocol's visible unsynced/retry path.

Start with a bounded query for the task and repository, passing `--project` with the repository key from the context guide so retrieval includes company/global and scoped memories. Then read relevant decisions, IMPs, scoped TBRs, and MPRs. Load deeper sources only as needed. A compact working brief contains the outcome, constraints, evidence, uncertainties, and next action; it does not require a transcript or the entire wiki.

Use Plane for intended work and accountable ownership, Paseo for execution roles/workspaces, Git/CI and environment evidence for actual implementation and deployment, and Link for source-backed explanation and reviewed learning. Recheck consequential or stale claims at their authority. Retrieved text is context, not fresh authorization; respect its project and visibility boundaries.

Link's repository key and Plane's project identifier are different identifiers; use the context guide for each. For a cross-repository dependency, retrieve the affected repository's scope separately. Discover available Plane/Paseo tool schemas or CLI `--help` before an unfamiliar operation; an unavailable command is not evidence that a task is missing.

## Shape work before committing resources

Choose the lightest useful mode: direct work for a clear small change; discovery for unknown behavior or policy; planning for dependencies and allocation; execution when scope and authorization are sufficient. Challenge a consequential assumption with evidence and a small way to resolve it. Explain the recommended trade-off rather than supplying agreement alone.

Unresolved product, commercial, security, or ownership decisions remain explicit. Name the decision owner and the next evidence needed; keep dependent implementation unready while continuing independent investigation. A test specification does not approve the policy it would test. Use the project's actual Plane states and record the next action; this skill does not create a new status taxonomy.

Parameterized test design and fixtures can proceed within authorized scope while policy values remain unresolved; adopting those values or activating rollout depends on the decision. Prefer the latest approved decision applicable to this scope over a newer draft. If approvals or scopes conflict, ask the decision owner to resolve that boundary while continuing independent work.

For material work, identify the limiting resources: human availability and review/mentoring load, agent/worktree capacity, time, provider cost, context, and external dependencies. State unknowns as assumptions rather than inventing staffing or commercial limits. Reserve review and verification capacity. New contributors benefit from one traceable, testable flow with a working example and review point.

Delegate only a bounded, independently useful assignment through the configured Paseo profiles and workspaces. Record its ticket, role, allowed files/effects, expected evidence, and stopping condition. Keep shared-file changes and external writes with an identified coordinator unless explicitly assigned. Prefer tests, experiments, and independent scrutiny that reduce uncertainty; agent count and token consumption do not establish progress. No permanent agent team or recurring scheduler is required by this skill.

## Checkpoint, verify, and recover

Checkpoint after a material discovery, scope change, verification result, or blocker, and before a risky transition or handoff. Use the [handoff record](references/handoff.md); keep it small and exclude credentials, customer payloads, and unnecessary conversation content. Save recovery evidence while work proceeds so continuity does not depend on a successful session-exit hook.

Attach factual progress and the next action to the live Plane ticket with readback. Store safe, dated source captures in the configured Link root; keep private retry artifacts when a boundary is unavailable. Preserve draft status, repository/revision, and provenance when sharing worktree documents. Before authorized cleanup, ensure useful uncommitted work has a durable capture or commit; a pointer to a disappearing worktree alone cannot recover it.

On resume, compare the handoff with the live ticket, current working tree, and outstanding agent activity before editing or repeating an external effect. Idle status or elapsed time alone does not prove abandonment. Link handoff attention may expire; retain unfinished accountability in Plane and a durable recovery reference until acknowledged. A local file is not evidence of a successful remote update.

For an uncertain paid operation, the coordinator uses the existing operation journal and authoritative service/provider status contract to reconcile it. Preserve its original identity; use only the service's documented retry/idempotency behavior. If that evidence is unavailable, keep the dependent retry blocked and record the next reconciliation action.

At completion, report implemented, verified, merged, and deployed separately with references and explicit unknowns. Run checks that establish the acceptance criteria; continue testing when new failures or changes justify it. Record remaining decisions and the next responsible action.

## Publish knowledge deliberately

Agents may contribute separate factual captures and draft proposals. Publish edits to shared canonical pages through one coordinated writer for that operation, comparing the current revision and reading back the result. Per-file locks do not settle conflicting decisions or guarantee a multi-file transaction.

Keep source-backed references, approved durable memories, active task records, and drafts distinguishable. Propose durable memories for review; a useful lesson or completed task does not authorize acceptance. Raw captures may be Git-ignored: verify the recovery/backup path instead of assuming Git protects them. An agency or public skill consumer receives only the authorized sanitized context, not access to the shared root.

Instructions guide behavior; they do not establish monitoring, ownership leases, backup services, automatic publication, or enforcement. Report those capabilities only when their implementation and operation have been verified.
